PIN-server protocol

OverviewGetting startedSecurity

ESPinServer follows the Blockstream/Jade PIN-server v2 blind-oracle shape for local interoperability testing. The complete implementation note is available as PINSERVER_PROTOCOL.md.

Listeners and messages

ListenerMessagesPurpose
HTTPS :443Browser pagesStorage-password entry, pairing, configuration, and diagnostics
HTTP :80POST /set_pin
POST /get_pin		Jade PIN-server API

HTTP envelope

Both API endpoints accept and return JSON with one base64 field:

{"data":"<base64 envelope>"}

After decoding, a request contains a 33-byte compressed secp256k1 client ephemeral public key, a 4-byte little-endian replay counter, and an authenticated encrypted payload.

Encrypted request

The payload is IV || AES-CBC ciphertext || HMAC-SHA256. AES-256-CBC uses PKCS#7 padding. ECDH derives a shared point, which is hashed and expanded with HMAC-SHA512 using the label blind_oracle_request; the first 32 bytes are the AES key and the second 32 bytes are the HMAC key.

The decrypted message is:

32 bytes   pin_secret = SHA256(user PIN)
0 or 32    client entropy (32 bytes required by /set_pin)
65 bytes   recoverable secp256k1 signature

The signature covers SHA256(client_ephemeral_key || replay_counter || pin_secret || entropy). Its recovered public key identifies the wallet record through SHA-256.

Responses and blind behavior

Responses use the same framing and the label blind_oracle_response. The decrypted response is one 32-byte key. /set_pin creates a random saved key; a valid /get_pin returns the HMAC-derived key share. Unknown or incorrect PINs receive a dummy response with the same shape instead of a direct failure.

Replay and rate limiting

Replay counters must increase for each stored client. Failed attempts trigger 5-second and 60-second cooldowns; the third failed attempt invalidates the record. Unknown records remain indistinguishable from normal protocol responses.

Storage encryption

The flash database is separate from the wire protocol. /pins.bin uses AES-256-CBC and HMAC-SHA256 with independent keys derived from the browser-created storage password by PBKDF2-HMAC-SHA256 with a per-database salt and 120,000 iterations.

For field offsets, key derivation, status codes, and the complete response flow, read the full technical description. This is experimental and unaudited firmware; use an isolated test network and test wallets only.

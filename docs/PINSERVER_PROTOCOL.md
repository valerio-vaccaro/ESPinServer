# ESPinServer PIN-server protocol

This document describes the messages implemented by ESPinServer for
Blockstream Jade PIN-server interoperability. It is a protocol implementation
note, not a security certification. The reference client and server behavior
are maintained in the [Blockstream Jade repository](https://github.com/Blockstream/Jade).

## Transport and access control

The firmware exposes two independent listeners:

| Listener | Purpose |
| --- | --- |
| HTTPS `443` | Browser pages, storage-password entry, configuration, pairing, and diagnostics |
| HTTP `80` | Jade API only: `/set_pin` and `/get_pin` |

The HTTPS certificate is self-signed and generated by the ESP32. The API
payload has its own authenticated encryption, but the HTTP transport still
exposes metadata such as endpoint, timing, and packet size. Use an isolated
trusted LAN and test credentials only.

Before the API is used, the encrypted PIN database must be unlocked through
the HTTPS browser interface. A new installation requires a 12–64 character
password containing uppercase, lowercase, a digit, and a printable symbol. The
password is never stored. Existing installations require the password once
after each reboot.

## HTTP messages

Both API endpoints accept only `POST`:

```http
POST /set_pin HTTP/1.1
Host: espinserver.local
Content-Type: application/json

{"data":"<base64 request envelope>"}
```

`/set_pin` creates or replaces the record associated with the recovered Jade
client public key. `/get_pin` verifies an existing record and returns the
stored key share only when the PIN is correct. Both return the same JSON
envelope shape:

```json
{"data":"<base64 response envelope>"}
```

Typical HTTP statuses are:

| Status | Meaning |
| --- | --- |
| `200` | Valid protocol response; incorrect or unknown PINs still receive a dummy response |
| `400` | Malformed JSON, invalid base64, failed authentication/decryption, bad signature, or replay |
| `403` | The record was invalidated after the third failed PIN attempt |
| `405` | The endpoint was not called with `POST` |
| `423` | Storage is still locked |
| `429` | Progressive failed-attempt cooldown is active |
| `500` | Internal key derivation, storage, or response-encryption failure |

The browser-only routes are not part of the Jade protocol. Requests to other
HTTP paths are redirected to HTTPS; API clients should use the port-80 URLs
shown on the Pairing page.

## Request envelope

After base64 decoding the value of `data`, the request bytes are:

| Offset | Length | Field |
| ---: | ---: | --- |
| `0` | `33` | `client_ephemeral_public_key`, compressed secp256k1 point |
| `33` | `4` | `replay_counter`, unsigned little-endian |
| `37` | remaining | Authenticated encrypted payload |

The encrypted payload is:

```text
16 bytes   AES-CBC IV
N bytes    AES-256-CBC ciphertext, including PKCS#7 padding
32 bytes   HMAC-SHA256 tag
```

The HMAC covers the IV and ciphertext (`IV || ciphertext`). The request key
schedule uses the ECDH shared point and the ASCII label
`blind_oracle_request`:

```text
shared_point = ECDH(server_ephemeral_private_key,
                    client_ephemeral_public_key)
compressed_shared_point = compressed(shared_point)
secret = SHA256(compressed_shared_point)
keys = HMAC-SHA512(secret, "blind_oracle_request")
AES_key = keys[0:32]
HMAC_key = keys[32:64]
```

The server rejects the message if the HMAC, ciphertext length, or PKCS#7
padding is invalid.

## Decrypted request message

After AES-CBC decryption and removal of PKCS#7 padding, the request contains:

```text
32 bytes   pin_secret
0 or 32    client_entropy
65 bytes   recoverable secp256k1 signature
```

The Jade normally derives `pin_secret` as `SHA256(user_pin)`. `client_entropy`
is required for `/set_pin` and omitted for `/get_pin`.

The signature is recovered against this SHA-256 message:

```text
SHA256(client_ephemeral_public_key || replay_counter ||
       pin_secret || client_entropy)
```

The recovered compressed client public key identifies the wallet record by:

```text
client_id = SHA256(recovered_client_public_key)
```

## Ephemeral server key

For each request, ESPinServer derives a deterministic server ephemeral private
key from the long-term server private key, the client ephemeral public key,
and the replay counter. In outline:

```text
hmac_key  = HMAC-SHA256(client_ephemeral_public_key, replay_counter)
root      = SHA256(hmac_key)
tweak     = BIP341_TapTweak(xonly(server_public_key), root)
server_ephemeral_private_key = normalized(server_private_key) + tweak mod n
```

The normalization and tweak construction match the Jade/libwally
TapTweak-compatible operation. The resulting key is used for the ECDH step;
the long-term server private key is not sent over the network.

## Response message

The response uses the same envelope format and the response label
`blind_oracle_response`:

```text
shared_point = ECDH(server_ephemeral_private_key,
                    client_ephemeral_public_key)
secret = SHA256(compressed(shared_point))
keys = HMAC-SHA512(secret, "blind_oracle_response")
```

The decrypted response is exactly 32 bytes: the final AES key share used by
the Jade PIN flow. The response is encrypted as:

```text
16 bytes   random IV
N bytes    AES-256-CBC(32-byte response with PKCS#7 padding)
32 bytes   HMAC-SHA256(IV || ciphertext)
```

For `/set_pin`, the server generates a random 32-byte `saved_key`, stores it,
and returns:

```text
final_key = HMAC-SHA256(saved_key, pin_secret)
```

For `/get_pin` with a valid PIN, it returns the same expression using the
stored key. For an unknown client or incorrect PIN, it uses a random dummy key:

```text
final_key = HMAC-SHA256(random_dummy_key, pin_secret)
```

This keeps the response shape uniform and avoids directly revealing whether a
client record or PIN was found.

## Replay protection and failed attempts

Each record stores the greatest accepted replay counter. A request is rejected
when its little-endian counter is not greater than the stored value. Existing
records also track failed attempts:

1. The first failed attempt is recorded.
2. The next attempt is delayed by 5 seconds.
3. The following attempt is delayed by 60 seconds.
4. The third failed PIN attempt invalidates the record.

Unknown records receive a dummy response without creating a record for
`/get_pin`. A successful `/set_pin` creates the first record for a new Jade.

## Encrypted database format

The protocol messages above are separate from the flash database. The file
`/pins.bin` contains a header, AES-CBC ciphertext, and a 32-byte HMAC tag. The
storage password derives independent AES and HMAC keys with PBKDF2-HMAC-SHA256
using a per-database salt and 120,000 iterations. The encrypted plaintext is
the fixed-size PIN record array; the password itself is never persisted.

## Security limitations

This is experimental firmware. The server private key and configuration are
stored in ESP32 NVS, and the device does not enable secure boot, flash
encryption, or a secure element. The HTTP API is intentionally plaintext at
the transport layer for Jade compatibility. A physical attacker able to read
or modify flash can extract or replace firmware, keys, and database data.

Use a trusted isolated network, disposable PINs, and test wallets only.
